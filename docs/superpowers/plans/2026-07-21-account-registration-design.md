# 账号自助注册设计

## 背景与目标

当前系统支持账号密码登录和游客身份登录，但账号用户只能通过 SQL 预置，前端没有自助注册入口。本次扩展在现有认证边界内增加最小可用的账号注册能力：用户使用账号和密码创建账号，注册成功后立即获得 JWT 并进入聊天界面。

本次范围仅包括账号、密码和确认密码，不引入邮箱、手机号、验证码、密码找回、第三方登录、用户资料、管理员审批或游客账号升级。

## 设计原则

- 复用现有 `ai_auth_user`、`AuthService`、JWT 签发和前端认证状态，不建立第二套用户体系。
- 注册成功响应与登录成功响应保持一致，前端沿用现有身份初始化流程。
- 密码只以 BCrypt 哈希入库，不记录、返回或打印明文密码。
- 前端校验用于即时反馈，后端独立执行全部安全和数据完整性校验。
- 数据库唯一索引是账号唯一性的最终边界，并正确处理并发注册竞争。
- 保留现有登录、游客身份和会话隔离行为。

## 交互设计

现有登录卡片增加“登录 / 注册”模式切换，默认显示登录模式。

登录模式保留：

- 账号输入框
- 密码输入框
- 登录按钮
- 游客进入按钮

注册模式显示：

- 账号输入框
- 密码输入框
- 确认密码输入框
- 创建账号按钮
- 游客进入按钮

模式切换时清理密码、确认密码和错误提示，账号输入可以保留。注册提交期间禁用模式切换、创建账号和游客进入按钮，避免重复提交。注册失败时保留账号，清空密码和确认密码，并将焦点移到第一个需要修正的字段或错误提示关联字段。

注册成功后复用现有 `submitAuthentication` 身份切换语义：停止活动流，清理旧身份的 token、用户、会话、消息、游标和临时错误，保存新 token 和用户信息，加载该用户的空会话列表并进入聊天界面。

## 输入规则

### 账号

- 去除首尾空白后参与校验和存储。
- 长度为 3-32 个字符。
- 仅允许 ASCII 字母、数字、下划线和连字符，正则为 `^[A-Za-z0-9_-]{3,32}$`。
- 唯一性沿用数据库 `account` 唯一索引及其排序规则；现有 MySQL 表默认排序规则下，大小写不作为不同账号。
- 登录接口继续兼容现有最长 128 字符的预置账号，不因注册规则收紧而破坏已有账号登录。

### 密码

- 长度为 8-72 个字符。
- 不自动去除首尾空白；空白属于密码内容。
- 不增加字符类别复杂度要求，避免形成不可解释的密码规则。
- 后端校验长度后使用 BCrypt 编码。

### 确认密码

- 仅存在于前端交互，不发送给后端。
- 必须与密码完全一致。

## HTTP 接口

新增公开接口：

```http
POST /api/v1/auth/register
Content-Type: application/json
```

请求体：

```json
{
  "account": "new_user",
  "password": "example-password"
}
```

成功时返回 HTTP 200，并复用现有登录响应：

```json
{
  "code": "200",
  "info": "success",
  "data": {
    "accessToken": "jwt-token",
    "tokenType": "Bearer",
    "expiresIn": 3600,
    "user": {
      "userId": "user_generated-id",
      "userType": "ACCOUNT",
      "account": "new_user"
    }
  }
}
```

失败响应：

- HTTP 400，`code = "400"`：账号或密码不符合规则。
- HTTP 409，`code = "409"`：账号已存在，包括并发插入触发唯一键冲突。
- HTTP 500，`code = "500"`：非预期注册失败，返回通用信息且不暴露数据库细节。

响应不得包含 `password` 或 `passwordHash`。认证过滤器将 `/api/v1/auth/register` 加入公开路径，其他 API 的保护规则不变。

## 后端设计

### 服务层

在现有 `AuthService` 增加 `register(account, password)`：

1. 规范化并校验账号。
2. 校验密码长度。
3. 查询账号是否已存在，存在时返回 `ACCOUNT_ALREADY_EXISTS`。
4. 生成 `user_` 加无连字符 UUID 的 `user_id`。
5. 构造 `ACCOUNT`、`ACTIVE` 用户并编码 BCrypt 密码哈希。
6. 调用现有 DAO `insert` 入库。
7. 捕获 `DuplicateKeyException` 并映射为 `ACCOUNT_ALREADY_EXISTS`，处理并发注册竞争。
8. 返回不含密码哈希的 `AuthUser`。

预查询只改善正常重复注册的响应；数据库唯一索引仍是最终一致性保障。注册不复用登录的 `INVALID_CREDENTIALS` 错误，因为注册场景需要明确告诉用户账号不可用。

`AuthFailureReason` 增加注册相关原因，控制器按原因映射 HTTP 状态，不根据异常消息做分支。

### 控制器

`AuthController` 增加 `RegisterRequest` 和 `/register` 方法。服务返回用户后调用现有 `authenticationResponse`，确保 JWT 内容、有效期和用户视图与登录完全一致。

### 数据层

现有 `ai_auth_user` 表已经满足注册需要：

- `user_id` 唯一且非空
- `account` 唯一
- `password_hash` 可存储 BCrypt 哈希
- `user_type` 和 `status` 支持账号用户

因此不新增表或迁移，不修改现有 DAO 接口和 MyBatis `insert` 语句。

## 前端设计

`index.html` 在现有登录卡片内增加模式切换和确认密码字段。模式切换使用带明确选中状态的分段控件，并同步 `aria-selected`、字段可见性、`autocomplete` 和标题文案。

注册提交前执行账号格式、密码长度和两次密码一致性校验。通过后调用：

```text
POST /api/v1/auth/register
```

请求只包含 `account` 和 `password`。成功响应交给现有认证提交结果处理逻辑；HTTP 409 显示“账号已存在”，HTTP 400 显示对应的账号或密码规则提示，其他错误显示“注册失败，请稍后重试”。

注册请求不携带现有身份 token。若页面内存中仍存在旧身份，只有在注册成功、即将应用新身份时才执行现有完整身份切换清理；注册失败不破坏当前认证状态。

## 数据流

```text
未登录 -> 切换注册模式 -> 输入账号、密码、确认密码
      -> 前端校验失败：就地提示并保留账号
      -> POST /api/v1/auth/register
          -> 后端校验失败：400
          -> 账号存在或唯一键竞争：409
          -> BCrypt 编码并插入 ACCOUNT/ACTIVE 用户
          -> 签发 JWT，返回登录同构响应
      -> 前端应用认证结果
      -> 加载新用户会话列表
      -> 进入聊天界面
```

## 安全与错误处理

- BCrypt 编码在服务端执行，持久层只接收哈希。
- 不在日志、异常消息、响应或前端持久化中保存密码。
- 注册接口使用与现有认证接口一致的 JSON 请求体大小和 Spring MVC 解析边界。
- 不改变现有 CORS 策略；部署环境应继续由反向代理限制可信来源。
- 本次不增加限流基础设施。公网开放前应在网关或反向代理为登录、游客和注册接口配置速率限制。
- 数据库错误只在明确识别为唯一键冲突时映射为账号已存在，其他数据库异常使用通用 500 响应。

## 测试设计

### 服务层测试

- 合法账号注册成功，生成 `user_` 前缀唯一 ID、`ACCOUNT` 和 `ACTIVE` 状态。
- 入库密码是可匹配原密码的 BCrypt 哈希，且不等于明文。
- 账号首尾空白被去除。
- 账号为空、过短、过长或包含非法字符时拒绝注册且不写库。
- 密码少于 8 或多于 72 个字符时拒绝注册且不写库。
- 已存在账号返回 `ACCOUNT_ALREADY_EXISTS`。
- 插入时唯一键竞争返回 `ACCOUNT_ALREADY_EXISTS`。

### 控制器与过滤器测试

- 注册成功返回 JWT、有效期和账号用户视图，不返回密码字段。
- 非法输入返回 400。
- 重复账号返回 409。
- 非预期失败返回通用 500。
- 注册接口无需 Bearer token，受保护接口规则保持不变。

### 前端测试

- 默认处于登录模式，切换注册模式显示确认密码。
- 切换模式清理密码、确认密码和错误状态。
- 非法账号、密码长度和确认密码不一致时不发请求。
- 注册请求只发送账号和密码。
- 注册成功复用身份保存并进入应用流程。
- 400、409 和网络失败显示对应提示并恢复按钮状态。
- 游客进入和既有登录流程没有回归。

## 验收标准

1. 未登录用户可以在现有登录卡片切换到注册模式。
2. 用户可以使用符合规则的账号和密码创建账号。
3. 注册成功后无需再次登录，直接进入聊天界面并获得独立会话空间。
4. 密码仅以 BCrypt 哈希存储，任何响应均不包含密码或密码哈希。
5. 重复账号在普通和并发场景下都不会创建第二条账号记录，并返回明确提示。
6. 前后端都执行输入校验，绕过前端无法写入非法账号。
7. 现有账号登录、游客进入、token 恢复、退出登录和会话隔离测试继续通过。
8. 桌面和移动端登录卡片无文本溢出、控件重叠或不可访问的键盘操作。

## 非目标与后续能力

本次不实现邮箱或手机验证、验证码、密码重置、账号注销、用户资料、游客升级、注册审批和第三方身份提供方。这些能力需要额外的数据字段和安全流程，应独立设计。
