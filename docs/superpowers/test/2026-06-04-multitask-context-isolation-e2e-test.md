# 多任务上下文隔离与按需依赖 E2E 回归测试说明

## 1. 文档目标

本文档用于指导后续 Agent 或开发人员，对“多任务上下文隔离与按需依赖”需求执行本地端到端回归测试（E2E Regression Test）。

本次测试对象是本地服务对外接口：

- `POST /api/v1/agent/auto_agent`

本文档关注的不是单个类或单个方法的局部逻辑，而是验证以下完整链路是否符合预期：

- 接口入口接收请求
- 意图路由节点拆分多任务
- 子任务按依赖关系执行
- 依赖任务结果按需注入后续任务 prompt
- 多任务结果统一汇总
- 当前轮多任务执行态被清理
- 多轮对话历史 `sessionHistory` 被保留

本文档要求执行测试的 Agent：

1. 使用真实本地服务接口进行调用；
2. 保留原始请求报文、原始响应报文和关键日志片段；
3. 不仅观察最终 response，还要按照本文档要求检查中间行为；
4. 对失败场景给出明确归因，区分“实现未满足需求”和“证据不足”。

---

## 2. 回归背景

本次需求对应的核心目标是：

1. 在多任务场景中，避免前一个子任务结果无条件污染后一个子任务；
2. 通过 `dependsOn` 表达必要依赖，仅在需要时传递前序任务结果；
3. 在当前轮 Query 完成后清理多任务执行态；
4. 保留用户级别会话历史 `sessionHistory`，支持多轮对话延续。

本次 E2E 回归重点不是验证“模型答得好不好”，而是验证：

- 多任务拆分是否正确表达依赖关系；
- 子任务执行是否符合“有依赖才注入、无依赖则隔离”的原则；
- 当前轮执行结束后是否清理干净；
- 下一轮是否还能继续承接用户级会话历史。

---

## 3. 本次强制验收点

### 3.1 验收点 A：拆分任务时生成 dependsOn

当用户输入中存在明显前后依赖关系时，`IntentRoutingNode` 拆分出的 `taskList` 中，对应 `SubTask` 应包含 `dependsOn` 字段。

要求：

- 有依赖的任务必须显式带 `dependsOn`
- 无依赖的任务可以为 `[]` 或 `null`
- 不允许所有任务都被默认串成依赖链
- 不允许本应存在依赖的任务完全缺失依赖表达

### 3.2 验收点 B：执行完成后清理多任务上下文

当前 Query 执行完成后，应清理当前轮多任务执行态，包括但不限于：

- `taskList`
- `originalMessage`
- `subTaskResults`
- 每个 `SubTask.result` 对应的运行态存储

清理目标是避免当前轮多任务数据污染下一轮 Query。

### 3.3 验收点 C：sessionHistory 保留

当前 Query 完成后，虽然多任务执行态需要清理，但用户级别会话历史 `sessionHistory` 必须保留，以支持下一轮对话继续承接上下文。

### 3.4 验收点 D：按需注入依赖结果

当 `SubTask.dependsOn` 非空时，当前任务执行前，需要将依赖任务的执行结果注入当前任务 prompt 中。

当 `SubTask.dependsOn` 为空时：

- 不应自动继承前一个任务结果
- 应直接使用当前任务原始内容执行

## 4. 执行测试前提

执行测试前，必须满足以下条件：

1. 本地服务已启动；
2. 本地接口可访问；
3. 使用固定测试用户，避免与其他会话混淆；
4. 每条测试用例使用独立 `sessionId`；
5. 测试执行过程中应能查看服务端日志；
6. 若无法查看日志，只能完成黑盒验证，不能确认全部验收点。

推荐约定：

- `userId=story-test`
- `sessionId` 统一按用例编号命名

例如：

- `story-mti-001`
- `story-mti-002`
- `story-mti-003`
- `story-mti-004`

---

## 5. 观测方式说明

本次回归分为两类观测方式。

### 5.1 黑盒观测

仅通过请求报文、响应报文和多轮会话表现判断。

适合验证：

- 最终回答是否体现依赖关系
- 多轮对话是否还能承接历史
- 无依赖任务是否出现明显串话
- 汇总结果是否逻辑合理

### 5.2 灰盒观测

需要结合服务端日志、调试输出或上下文打印。

适合验证：

- `taskList` 中是否真实存在 `dependsOn`
- 子任务执行前的 `executableContent` 是否已注入依赖结果
- `subTaskResults` 是否在汇总后被清理
- `taskList/originalMessage` 等多任务 key 是否被清理
- `sessionHistory` 是否保留而未被误删

### 5.3 结果可信度要求

- 仅有黑盒证据：只能说明外部行为表象正常或异常，不能证明内部实现完全符合设计
- 同时具备灰盒证据：才可以确认对应验收点真正通过

## 8. 标准测试用例

### TC-E2E-MTI-001：dependsOn 生成验证

#### 目的

验证 `IntentRoutingNode` 在拆分存在前后依赖的用户请求时，是否为相应 `SubTask` 生成 `dependsOn` 字段。

#### 请求报文

```json
{
  "userId": "story-test",
  "sessionId": "story-mti-001",
  "message": "解释向量数据库的概念；基于向量数据库介绍RAG；再单独对比RAG和微调",
  "maxStep": 10,
  "inputType": 0,
  "agentType": "default"
}
```

#### 预期观察点

- 应拆分出 3 个子任务
- “基于向量数据库介绍RAG”的子任务应依赖“解释向量数据库的概念”
- “对比RAG和微调”应为独立任务，通常不依赖前两个任务

#### 灰盒验证要求

需要从日志或中间输出中确认：

- `taskList` 至少包含 3 个 `SubTask`
- 第二个子任务存在 `dependsOn=["sub-1"]` 或等价依赖表达
- 第三个子任务 `dependsOn=[]` 或 `null`

#### 黑盒辅助判断

最终回答中：

- 第二部分应明显建立在第一部分定义之上
- 第三部分应可独立理解，而不是完全依赖前文

#### 通过标准

满足以下全部条件判定通过：

1. 有依赖的子任务显式携带 `dependsOn`
2. 无依赖任务未被错误地串联依赖
3. 最终输出符合依赖与独立任务的预期语义

#### 失败归因提示

- 如果没有日志，仅能得出弱结论
- 如果日志显示所有任务都无 `dependsOn`，判定实现未满足需求

---

### TC-E2E-MTI-002：依赖结果注入验证

#### 目的

验证存在 `dependsOn` 的子任务，在执行前是否会把依赖任务的 `result` 注入到当前任务 prompt 中。

#### 请求报文

```json
{
  "userId": "story-test",
  "sessionId": "story-mti-002",
  "message": "先解释MCP是什么；再基于上面的解释，说明它和普通API集成有什么区别",
  "maxStep": 10,
  "inputType": 0,
  "agentType": "default"
}
```

#### 预期观察点

- 第一个子任务产出 MCP 的基础定义
- 第二个子任务依赖第一个子任务
- 第二个子任务执行时，其 prompt 中应已包含第一个子任务的结果，而不是保留占位符或空依赖

#### 灰盒验证要求

需要从日志中确认：

- 第二个子任务存在 `dependsOn`
- 第二个子任务执行前的 `executableContent` 已注入依赖结果
- 不应保留原始依赖占位符

#### 黑盒辅助判断

最终回答中第二部分应明显基于第一部分的解释展开，而不是像重新回答一个无上下文的新问题。

#### 通过标准

满足以下全部条件判定通过：

1. 第二个任务存在依赖关系
2. 执行前 prompt 已注入依赖结果
3. 最终回答体现出依赖式展开

#### 失败归因提示

- 如果 `dependsOn` 存在但注入内容为空，判定依赖结果传递未生效
- 如果最终回答看起来合理，但没有日志证明，只能记为“弱通过”或“证据不足”

---

### TC-E2E-MTI-003：无依赖任务独立执行验证

#### 目的

验证无依赖的多个子任务会使用干净上下文独立执行，而不会自动继承前一个任务的结果。

#### 请求报文

```json
{
  "userId": "story-test",
  "sessionId": "story-mti-003",
  "message": "解释Spring AI；介绍MyBatis；说明Docker Compose的作用",
  "maxStep": 10,
  "inputType": 0,
  "agentType": "default"
}
```

#### 预期观察点

- 应拆分为多个相互独立的任务
- 各任务 `dependsOn` 应为空、缺失或明确表示无依赖
- 各任务执行时应直接使用原始内容，不应引入前序任务结果

#### 灰盒验证要求

需要从日志中确认：

- 各子任务 `dependsOn` 为空
- 执行前 `executableContent` 与原始 `content` 等价
- 未出现自动注入前置结果的行为

#### 黑盒辅助判断

最终回答中三部分内容应主题清晰、边界明确，不应出现明显串话现象。

#### 通过标准

满足以下全部条件判定通过：

1. 无依赖任务未被错误添加依赖
2. 执行内容未注入无关前置结果
3. 最终回答未出现明显上下文污染

#### 失败归因提示

如果任务之间明显出现内容串扰，应结合日志判断：

- 是模型偶发发挥导致
- 还是执行上下文确实被污染

---

### TC-E2E-MTI-004：清理与 sessionHistory 保留验证

#### 目的

验证当前 Query 执行完成后，多任务执行态被清理，但 `sessionHistory` 仍然保留，可用于下一轮对话。

#### 测试步骤

##### 第一步：发起多任务请求

```json
{
  "userId": "story-test",
  "sessionId": "story-mti-004",
  "message": "解释向量数据库；介绍RAG；对比RAG和微调",
  "maxStep": 10,
  "inputType": 0,
  "agentType": "default"
}
```

##### 第二步：同一 sessionId 发起追问

```json
{
  "userId": "story-test",
  "sessionId": "story-mti-004",
  "message": "继续刚才的话题，给我一个实际应用案例",
  "maxStep": 10,
  "inputType": 0,
  "agentType": "default"
}
```

#### 预期观察点

- 第一轮执行完成后，多任务临时执行态应被清理
- 第二轮仍能承接“向量数据库 / RAG / 微调”相关上下文
- 第二轮不应错误复用第一轮的 `taskList` 或 `subTaskResults`

#### 灰盒验证要求

需要从日志确认：

- 第一轮完成后触发清理
- `subTaskResults` 被清理
- `taskList/originalMessage` 等多任务 key 被清理
- `sessionHistory` 未被清理

#### 黑盒辅助判断

第二轮回答如果能自然承接上一轮主题，说明 `sessionHistory` 大概率仍然可用。

#### 通过标准

满足以下全部条件判定通过：

1. 当前轮多任务执行态被清理
2. 下一轮对话仍保留会话语义
3. 未出现上一轮子任务执行态直接泄漏到下一轮的现象

#### 失败归因提示

特别注意：

- 如果第二轮能接上话题，不等于一定完成了多任务上下文清理
- 如果日志显示未清理，应判定验收点 B 失败，即使第二轮回答看起来正常

## 9. 执行建议顺序

建议后续测试 Agent 按照以下顺序执行：

1. 先跑 `TC-E2E-MTI-001`，确认依赖是否被识别和表达；
2. 再跑 `TC-E2E-MTI-002`，确认依赖结果是否真正注入；
3. 再跑 `TC-E2E-MTI-003`，确认无依赖任务不会被污染；
4. 最后跑 `TC-E2E-MTI-004`，确认清理与会话保留逻辑；
5. 每跑完一条用例，立即记录请求、响应、日志和结论；
6. 如发现行为与设计不一致，先输出差异分析，不要直接修改代码。

## 10. 失败归因规则

### 10.1 response 正常但日志缺失

如果最终回答看起来符合预期，但没有日志证明：

- `dependsOn` 是否存在
- prompt 是否注入依赖结果
- 上下文是否完成清理

则不能直接判定“完全通过”，应标记为：

- `证据不足（黑盒行为正常）`

### 10.2 第二轮会话能承接上下文，但未见清理日志

这种情况只能说明 `sessionHistory` 大概率保留，
不能说明多任务执行态一定已清理。

应判定：

- 验收点 C 倾向通过
- 验收点 B 仍需灰盒证据确认

### 10.3 日志显示未清理

若日志明确显示：

- `subTaskResults` 未清理
- `taskList` 未清理
- `originalMessage` 未清理

则直接判定验收点 B 失败。

### 10.4 模型输出不稳定

如果多次重复调用，拆分结果波动较大：

- 应记录为模型稳定性风险
- 不应直接把所有失败归因为代码逻辑错误
- 但若连续多次无法生成应有依赖关系，仍可判定需求未稳定达成

## 11. 当前实现风险提示

根据当前代码实现，以下风险需要重点关注：

1. `DynamicContext` 已提供清理方法：
   - `clearSubTaskResults()`
   - `clearMultiTaskContext()`

2. 但是否在当前主流程中真正触发清理，需要通过实际执行和日志再次确认。

3. 因此：
   - 验收点 A、D 相对更容易观测；
   - 验收点 B 存在较高失败概率；
   - 验收点 C 需要通过多轮会话验证；
   - 若清理相关用例失败，应优先判断为实现可能尚未闭环，而非优先怀疑测试脚本有误。

## 12. 对执行测试 Agent 的要求

执行本测试文档时，Agent 应满足以下要求：

1. 不要只看最终 HTTP response；
2. 必须显式说明每条用例是黑盒验证还是灰盒验证；

5. 所有结论都应回扣到本文档第 3 章的 4 个强制验收点；
6. 若发现实现与设计不一致，应输出差异点，而不是自动修正文档标准。
