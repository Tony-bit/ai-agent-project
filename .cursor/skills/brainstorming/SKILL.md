# 头脑风暴：将想法转化为设计

通过自然的协作对话，将想法转化为完整的设计和规格。

首先理解当前项目上下文，然后一次问一个问题来完善想法。一旦理解要构建什么，呈现设计并获得用户批准。

<硬性门槛>
在呈现设计并获得用户批准之前，**不要**调用任何实现 skill，不要写任何代码，不要搭建任何项目，不要采取任何实现行动。这适用于所有项目，无论感知到的复杂度如何。
</硬性门槛>

## 反模式："这太简单了不需要设计"

每个项目都要经过此流程。任务清单、单个函数工具、配置更改——都是。"简单"项目正是未经审视的假设造成最多浪费工作的地方。设计可以很短（真正简单的项目几句话即可），但必须呈现并获得批准。

## 检查清单

必须为以下每个项目创建任务并按顺序完成：

1. **探索项目上下文** — 检查文件、文档、最近的提交
2. **提供视觉伴侣**（如果主题涉及视觉问题）— 这是单独的消息，不与澄清问题合并
3. **提出澄清问题** — 一次一个，理解目的/约束/成功标准
4. **提出 2-3 种方案** — 包含权衡和你的推荐
5. **呈现设计** — 按复杂度缩放各部分，每部分后获得用户批准
6. **编写设计文档** — 保存到 `docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md` 并提交
7. **规格自审** — 快速检查是否有占位符、矛盾、歧义、范围问题（见下文）
8. **用户审阅书面规格** — 要求用户在继续前审阅规格文件
9. **过渡到实现** — 调用 writing-plans skill 创建实现计划

## 执行流程

```
探索项目上下文
  → 需要视觉问题？
      → 提供视觉伴侣（单独消息）
      → 提出澄清问题
  → 提出 2-3 种方案
  → 呈现设计各部分
  → 用户批准？
      → 否：修订
      → 是：写设计文档
  → 规格自审（内联修复）
  → 用户审阅？
      → 需要更改：重新写
      → 批准：调用 writing-plans
```

**最终状态是调用 writing-plans。** 不要调用 frontend-design、mcp-builder 或任何其他实现 skill。头脑风暴后唯一调用的 skill 是 writing-plans。

## 流程详解

**理解想法：**

- 首先了解当前项目状态（文件、文档、最近的提交）
- 在问详细问题之前，评估范围：如果请求描述了多个独立子系统（例如"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记。不要在需要先分解的项目上花时间完善细节
- 如果项目太大无法作为单一规格，帮助用户分解为子项目：有哪些独立的部分，它们如何关联，应该按什么顺序构建？然后对第一个子项目进行正常的头脑风暴设计流程。每个子项目获得自己的规格 → 计划 → 实现循环
- 对于适当范围的项目，一次问一个问题来完善想法
- 可能时优先使用选择题，开放式也可以
- 一次只问一个问题
- 专注于理解：目的、约束、成功标准

**探索方案：**

- 提出 2-3 种不同方案，包含权衡
- 以对话方式呈现选项，包含推荐和理由
- 先提出推荐选项并解释原因

**呈现设计：**

- 一旦认为理解了要构建什么，呈现设计
- 按复杂度缩放每个部分：直接的用几句话，复杂的用 200-300 字
- 每部分后询问是否正确
- 涵盖：架构、组件、数据流、错误处理、测试
- 准备好在有问题时回退澄清

**设计要隔离和清晰：**

- 将系统分解为更小的单元，每个单元有一个明确目的，通过定义良好的接口通信，可以独立理解和测试
- 对于每个单元，你应该能够回答：它做什么，怎么用，依赖什么？
- 有人能在不阅读内部实现的情况下理解单元做什么吗？能改变内部实现而不破坏消费者吗？如果不能，边界需要改进

**在现有代码库中工作：**

- 在提出更改前探索当前结构。遵循现有模式
- 如果现有代码有问题影响工作（如一个变得太大的文件、模糊的边界、纠缠的职责），将针对性改进作为设计的一部分——就像一个好开发者在工作的代码中改进代码一样
- 不要提出无关的重构。专注于当前目标的服务

## 设计之后

**文档：**

- 将验证的设计（规格）写入 `docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`
- 将设计文档提交到 git

**规格自审：**
编写规格文档后，用新眼光审视：

1. **占位符扫描：** 有任何"TBD"、"TODO"、不完整部分或模糊需求吗？修复它们。
2. **内部一致性：** 任何部分相互矛盾吗？架构与特性描述匹配吗？
3. **范围检查：** 这个范围是否足够集中于单一实现计划，还是需要分解？
4. **歧义检查：** 任何需求可以用两种不同方式解释吗？如果是，选择一个并明确。

内联修复任何问题。无需重新审查——直接修复然后继续。

**用户审阅门槛：**
规格审查循环通过后，要求用户在继续前审阅书面规格：

> "规格已编写并提交到 `<路径>`。请审阅，如果想在开始写出实现计划前做任何更改，请告诉我。"

等待用户响应。如果他们请求更改，进行更改并重新运行规格审查循环。只有在用户批准后才能继续。

**实现（重要！）：**

- 调用 `writing-plans` skill 创建详细实现计划
- **不要调用任何其他 skill。writing-plans 是下一步。**
- **开始实现前，必须读取 `isolated-worktree-setup` skill 并执行隔离协议**

## 关键原则

- **一次只问一个问题** — 不要用多个问题压倒用户
- **优先选择题** — 比开放式更容易回答
- **YAGNI 严格** — 从所有设计中删除不必要的特性
- **探索替代方案** — 在确定前始终提出 2-3 种方案
- **增量验证** — 呈现设计，获得批准后再继续
- **保持灵活** — 有问题时回退澄清
