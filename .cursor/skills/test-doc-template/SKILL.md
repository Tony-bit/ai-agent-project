# 测试文档与测试用例设计模板

## 概述

此 skill 用于在本项目中编写测试文档、测试方案、测试用例设计和提测材料。

目标：
- 让测试文档与 Story 文档强关联
- 让测试场景覆盖正常、异常、边界、回归四类风险
- 让测试执行和验收都有明确 `status`
- 保持“只测本层逻辑，中间件统一 mock”的项目约束

## 何时使用

当出现以下任一情况时使用：
- 用户要求补充测试文档、测试方案、测试用例设计、提测文档、验收用例、回归清单
- 已有 Story 文档，需要补齐配套测试设计
- 已有 OpenSpec change，需要补齐配套验证材料
- 需求进入实现、联调、提测或验收阶段，需要明确验证范围和验收标准
- 需要把测试场景映射到具体测试类/测试方法

以下情况通常不需要单独使用本 skill：
- 只是补一个非常小的单元测试，且不需要成体系测试文档
- 只是口头说明“测一下”而不需要形成文档或模板

## 输出原则

1. **先关联 Story，再写测试文档**
   - 测试文档必须显式引用对应 Story 路径
   - 测试范围、验收标准、回归点要从 Story 的目标、设计、任务拆解中反推

2. **测试文档只描述验证，不重复实现设计**
   - Story 负责 why / what / how
   - Test 文档负责 how to verify / acceptance / regression

3. **遵守项目测试规则**
   - 中间件依赖统一 mock，只测试当前层业务逻辑
   - 每个测试用例最终应以 assert 比对结果结束
   - 如涉及异常、重试、超时、降级、异步清理等行为，必须单列场景覆盖

4. **文档必须可执行**
   - 测试场景不要写空话，必须能落到测试代码、验证步骤或验收动作
   - 每个执行项和验收项需要 `status` 字段

5. **测试文档路径必须固定**
   - 测试文档统一放在 `docs/superpowers/test/`
   - 不要放到业务域目录、临时目录或其他 docs 子目录

## 推荐文件命名与存放路径

测试文档应统一存放在：

```text
docs/superpowers/test/
```

推荐文件命名：

```text
docs/superpowers/test/YYYY-MM-DD-<topic>-test.md
```

示例：

```text
docs/superpowers/test/2026-06-05-multitask-context-isolation-test.md
```

## 测试场景分层规范

统一使用四层场景：

1. **正常场景**：主流程是否成立
2. **异常场景**：失败、缺参、空值、异常传播、兜底逻辑是否正确
3. **边界场景**：空集合、单元素、超长输入、链式依赖、极限值等
4. **回归场景**：旧功能、相邻流程、公共能力是否被破坏

## 编号规范

建议统一编号：

- `TC-001 ~ TC-099`：正常场景
- `TC-101 ~ TC-199`：异常场景
- `TC-201 ~ TC-299`：边界场景
- `TC-301 ~ TC-399`：回归场景
- `AC-001 ~`：验收项
- `BUG-001 ~`：问题记录

## 测试方法命名建议

测试方法建议统一使用：

```java
should_xxx_when_xxx
```

示例：

```java
should_not_inherit_previous_subtask_context_when_no_dependency
should_inject_dependency_result_when_depends_on_present
should_clear_multi_task_context_after_query_complete
```

## 编写质量要求

在输出测试文档前，做一次快速自检：

- 是否引用了对应 Story 路径
- 是否区分了测试范围与不测范围
- 是否覆盖正常 / 异常 / 边界 / 回归四类场景
- 是否体现 mock 策略与本层测试原则
- 是否给出了验收标准和执行状态字段
- 是否能映射到真实测试类或测试方法

## 与执行类 skill 的协作

- 当执行 Story / plan 时，如果需要补充测试文档、测试用例设计、提测材料，应读取本 skill
- 当实现完成准备验证时，测试文档可作为验收和回归检查清单
